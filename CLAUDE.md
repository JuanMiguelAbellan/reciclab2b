# ReciclaB2B — instrucciones para Claude Code

Plataforma privada B2B (generadores de cartón/plástico reciclable ↔ compradores). Monolito Laravel 13 + Inertia.js + React + TypeScript + Tailwind, con Filament para el panel admin y Laravel Reverb (WebSockets propios) para mensajería en tiempo real. Entorno de desarrollo: Docker/Sail (ver README).

**Antes de nada: lee la sección "Estado del proyecto" de `README.md`** para saber qué fases están hechas y cuál es el siguiente paso pendiente.

## Reglas de trabajo (vigentes durante todo el proyecto)

1. Construye por fases pequeñas y verificables. No avances a una fase nueva sin confirmar que la anterior funciona.
2. Antes de cambios importantes: explica qué vas a hacer, qué archivos tocarás y por qué, antes de tocarlos.
3. No instales dependencias sin explicar antes por qué son necesarias.
4. Backend: Laravel (Actions/Services, Form Requests, Policies, Enums). Nada de lógica de negocio en controladores ni en componentes React.
5. Frontend: React + TypeScript estricto + Inertia (nada de Axios/fetch manual salvo casos puntuales justificados). Nada de Redux salvo necesidad demostrada.
6. Inglés para nombres de clases/tablas/variables/rutas internas. Español para todo texto visible en la interfaz.
7. Toda ruta privada debe estar protegida por middleware **y** por Policies que comprueben propiedad/estado real, no solo el nombre del rol (ver `CompanyPolicy`, `UserPolicy` como ejemplo).
8. Valida siempre en el backend (Form Requests). La validación en frontend es solo UX.
9. Añade tests (`php artisan test`) para funcionalidad crítica (auth, autorización, validaciones) y ejecútalos tras cambios relevantes.
10. Antes de comandos destructivos (`migrate:fresh`, `db:wipe`, borrar archivos): avisa y explica.
11. No hagas `git push` salvo que se pida explícitamente. Nunca reescribas el historial ni hagas `reset --hard` sin autorización expresa.
12. Al terminar cada fase o checkpoint: resume qué se hizo, cómo probarlo manualmente, y cuál es el siguiente paso.

## Restricciones tecnológicas duras

No usar: WordPress, PrestaShop, Next.js, Vue, Angular, una API REST completa/SPA separada, Sanctum para SPA externa, Blade para las páginas principales (solo para la plantilla raíz de Inertia, correos, Filament), Livewire en el frontend principal (sí dentro de Filament, es interno).

## Decisiones ya tomadas (no las repitas ni las cuestiones sin motivo)

- **Entorno**: Laravel Sail, invocado con `docker compose` directamente (el script `./vendor/bin/sail` no funciona en Git Bash/Windows sin WSL2). Se trabaja indistintamente desde Windows+Docker Desktop y Linux+Docker nativo (dos máquinas distintas) — ver "Notas de entorno" en README para los problemas ya resueltos de cada una (permisos de `storage/`, polling de Vite, corrupción de Docker Desktop, propiedad de archivos creados por `docker compose exec` como root).
- **Panel admin**: Filament 4 en `/admin`, acceso restringido a `superadmin`/`admin` aprobados vía `User::canAccessPanel()`. Las acciones de aprobar/rechazar/bloquear (usuarios y empresas) son `Filament\Actions\Action` a medida que asignan `status`/`approved_at`/`approved_by` y llaman a `save()` directamente — esos campos no son mass-assignable a propósito, así que no uses formularios/ediciones genéricas de Filament para cambiarlos.
- **Auth**: Laravel Fortify (headless) + páginas Inertia/React propias en `resources/js/pages/auth/`.
- **Roles/permisos**: Spatie Laravel Permission. Roles: `superadmin`, `admin`, `producer`, `buyer` (ver `App\Enums\RoleName`).
- **User**: campos `first_name`/`last_name` (no `name`), con `status` (`App\Enums\UserStatus`) y aprobación manual desde el panel de Filament (`/admin`).
- **Company**: `App\Enums\CompanyType` / `CompanyStatus`, relación `company_user` con `is_primary`.
- **Offer**: `App\Enums\MaterialType` (cartón/plástico) / `OfferStatus` (`draft/published/paused/closed`, ciclo definido en `OfferPolicy` + Actions `Publish/Pause/CloseOfferAction`). Cualquier miembro de una empresa **aprobada** (no solo el principal) puede crear/gestionar sus ofertas — a diferencia de `CompanyPolicy::update`, que sí restringe al principal.
- **Mercado** (`/mercado`, `MarketplaceController`): el listado de ofertas publicadas es visible para **cualquier** usuario aprobado con empresa aprobada (no solo rol `buyer` — también productores, para ver precios de mercado). El detalle de la oferta muestra también el contacto (teléfono/email) de la empresa vendedora, además del botón "Contactar".
- **`Offer::isTradeable()`**: publicada + empresa vendedora aprobada. Úsalo (no repitas la comprobación a mano) en cualquier sitio nuevo donde un comprador pueda actuar sobre una oferta — ya lo usan `ConversationPolicy::startFor` y `OrderPolicy::placeFor`. Para listados usa el scope `Offer::visibleInMarket()` (= `published()` + empresa aprobada), deliberadamente separado de `published()` (que solo mira el propio ciclo de vida de la oferta). Si añades una acción nueva de comprador sobre una oferta y no pasa por uno de estos dos sitios, probablemente te estás dejando el mismo hueco que ya hubo que cerrar en la Fase 13: nada más comprobaba que la empresa vendedora no estuviera bloqueada.
- **`CloseOfferAction`** pide `User $user` (además de `Offer $offer`) y rechaza automáticamente cualquier pedido pendiente de esa oferta (reutiliza `RejectOrderAction`, con mensaje propio). Si escribes una Action/lugar nuevo que pueda dejar una oferta con pedidos pendientes en un estado sin salida (cerrada, rechazada, lo que sea que signifique "ya no se puede aceptar"), resuelve esos pendientes explícitamente — no asumas que quedarán bien solos, ya nos pasó dos veces (Fase 13 con `isTradeable`, Fase 14 con esto).
- **Mensajería** (`/mensajes`, `ConversationController`, Reverb): una conversación por (`offer_id`, `buyer_company_id`) — se reutiliza si se pulsa "Contactar" varias veces en la misma oferta. Participan los miembros de ambas empresas (`ConversationPolicy`), no solo el principal. Evento `MessageSent` como `ShouldBroadcastNow` (sin cola) en canal privado `conversation.{id}`. El frontend (`pages/conversations/Show.tsx`) no usa la respuesta del POST para pintar mensajes — todo llega por WebSocket, incluidos los propios (evita duplicados sin necesitar `toOthers()`). Requiere `php artisan reverb:start` corriendo (ver README) además de `npm run dev`.
- **Mass assignment**: patrón recurrente en este proyecto — las FKs/columnas de workflow que un usuario no debe poder falsificar (`approved_by`, `approved_at`, `status`, `created_by`, `offer_id`/`buyer_company_id` en `Conversation`, `conversation_id`/`sender_id` en `Message`...) se dejan **fuera** de `#[Fillable]` a propósito. Si necesitas asignarlas desde una Action/controlador, hazlo por asignación directa de propiedad + `save()` (nunca `create([...])`/`update([...])` con esos campos — se ignorarían en silencio, sin error).
- **Perfil de empresa** (`/empresa`, `CompanyController`): reutiliza `CompanyPolicy::update` (solo el responsable principal edita; el resto de miembros ven en solo lectura). Añadir miembro por email solo funciona si esa persona ya tiene cuenta aprobada y sin empresa — no hay invitaciones por correo (no hay SMTP configurado, es a propósito, mismo criterio que "Contactar" en el mercado). No se puede quitar al responsable principal (`RemoveCompanyMemberAction` lo bloquea).
- **Mensajes no leídos**: `conversation_reads` guarda el **id** del último mensaje visto por usuario+conversación (no un timestamp — con timestamp, un `save()` y un mensaje casi simultáneos podían empatar por precisión de reloj y quedar mal marcado; con id es determinista, ya nos pasó una vez). El contador (`User::unreadConversationsCount()`) se comparte vía Inertia en `auth.user.unread_conversations_count` desde `HandleInertiaRequests`. **Es tiempo real**: `MessageSent::broadcastOn()` transmite también en el canal privado personal de cada destinatario (`App.Models.User.{id}`), y `AppLayout` lo escucha y hace `router.reload({ only: ['auth'] })` al recibirlo — recalcula en servidor, no duplica la lógica en el cliente. `echo` se importa dinámicamente en `AppLayout` (no de forma estática) para que laravel-echo/pusher-js no engorden el bundle de páginas que no usan mensajería, mismo criterio que con Leaflet.
- **Idioma app**: `APP_LOCALE=es`, traducciones en `lang/es/`.
- **Dashboard** (`DashboardController@index`, ruta `/dashboard`): ya no es el placeholder de la Fase 2. Si `$user->primaryCompany()` es `null` (personal sin empresa, que pasa el middleware `has-company` porque está exento), la vista recibe `company: null` y muestra una versión mínima — no asumas que siempre hay empresa al tocar esta página.
- **Ubicación de ofertas**: `Offer` tiene coordenadas exactas (privadas, `exact_latitude`/`exact_longitude`, rellenadas por el propietario en un mapa Leaflet de clic-para-marcar) y públicas (`public_latitude`/`public_longitude`, desplazadas de forma determinista con `App\Support\ApproximateLocation` — mismo seed y coordenadas siempre dan el mismo resultado, no se recalcula aleatoriamente en cada carga). Las públicas se recalculan en `Offer::refreshPublicLocation()`, llamado por las Actions de crear/editar antes de `save()`; no son `#[Fillable]` (mismo patrón de mass assignment del resto del proyecto). `MarketplaceController` **nunca** serializa las coordenadas exactas (ni siquiera para el propio dueño viendo su oferta publicada); si necesitas mostrárselas al dueño, es desde `OfferController` (páginas de gestión, ya protegidas por `OfferPolicy`). Leaflet se importa (CSS + fix de iconos, ver `resources/js/components/map/leafletIcons.ts`) dentro de los propios componentes de mapa, no en `app.tsx`, para que quede en un chunk aparte y no engorde el bundle principal.
- **Invitaciones de empresa** (`CompanyInvitation`, `/empresa` → "Invitar por email"): solo para emails sin cuenta todavía; si ya existe cuenta, se usa el flujo de "añadir miembro" que ya existía. El correo se envía de verdad vía **Mailpit** (`compose.yaml`, ver <http://localhost:8025> en local) usando `MAIL_MAILER=smtp`; en producción hay que cambiar las credenciales SMTP en `.env`. El enlace es una URL firmada (`URL::temporarySignedRoute`, 7 días) — el formulario de aceptación hace POST a esa **misma URL completa** (prop `acceptUrl`, no a una ruta con nombre aparte), porque el middleware `signed` valida la query string entera; si generas una ruta nueva protegida con `signed`, recuerda este patrón.
- **Notificaciones de cambio de estado** (`UserStatusChangedNotification`, `CompanyStatusChangedNotification`): se disparan desde las Actions de Filament (`UsersTable`/`CompaniesTable`) tras aprobar/rechazar/bloquear, mismo Mailpit que las invitaciones. `Company` no es `Notifiable` (solo `User` lo es) — para notificar a una empresa, usa `Company::primaryMember()` y notifica a ese `User`; si no tiene responsable principal todavía, no pasa nada (no lances excepción, comprueba null). Si añades un nuevo cambio de estado que el usuario deba conocer (nueva transición, nuevo modelo), sigue este mismo patrón en vez de asumir que el usuario ya se enterará por su cuenta — ya nos hemos encontrado dos veces con acciones de Filament que solo avisaban al admin, nunca al afectado.
- **Divergencia deliberada del spec original**: no existe `Production`/`Product`/`Variety`/`Certification` (catálogo) ni el modelo de precios (Fijo/Indicativo/A consultar/Oculto) ni validación de un admin antes de publicar — se decidió mantener `Offer` tal cual (más simple) en vez de retrofitting. Tampoco existe `Inquiry` de solo petición/respuesta: hay chat en tiempo real completo (Reverb), que el spec original pedía explícitamente NO construir en la v1 — se mantuvo porque ya funcionaba y se decidió aceptarlo como mejora. No repropongas estos cambios sin que el usuario lo pida.
- **Pedidos** (`Order`, `/pedidos`, `OrderPolicy` + Actions `Place/Accept/Reject/Complete/CancelOrderAction`): se puede pedir desde la oferta (`/mercado/{offer}/pedidos`) o desde dentro de una conversación (`/mensajes/{conversation}/pedidos`) — ambos acaban creando/reutilizando la misma `Conversation`. Solo el vendedor acepta/rechaza/completa; el comprador cancela mientras está pendiente, cualquiera de las dos partes una vez aceptado. **Con control de inventario**: `Offer::availableQuantity()` = cantidad − pedidos aceptados/completados, recomprobado tanto al pedir como al aceptar (evita sobreventa por condición de carrera). Si aceptar agota la oferta, se cierra sola — y **no se reabre** si luego se cancela ese pedido (closing-is-final ya establecido en Fase 4 gana sobre reabrir por cancelación; limitación conocida, documentada en README). Cada Action de transición (`Accept/Reject/Complete/CancelOrderAction`) inyecta `SendMessageAction` y publica un mensaje en la conversación del pedido (si tiene una) tras cambiar el estado — es como se notifica a la otra parte, sin sistema de notificaciones aparte.
- **Gotcha de `Gate::authorize`/`->can()` con array de contexto**: `$user->can('ability', [Clase::class, $modelo])` usa **Clase::class únicamente para elegir qué Policy resolver** (no se pasa como argumento al método) — si pones la clase equivocada ahí, Laravel resuelve la Policy equivocada, el método no existe en ella, y la ability devuelve `false` **en silencio** (sin excepción, indistinguible de un "no autorizado" legítimo). Ya nos pasó con `OrderPolicy::placeFor` (puse `Offer::class` por copiar el patrón de `ConversationPolicy::startFor` sin fijarme, cuando debía ser `Order::class`). Compruébalo con un test que espere `true`, no solo `false` — un test que solo verifica denegación no lo detecta.
- **`User::company()` vs `User::primaryCompany()`** (Fase 16, hueco real encontrado en auditoría): son cosas distintas y el nombre de la segunda invita a confundirlas. `company()` = la empresa a la que pertenece el usuario, sea o no el responsable principal (úsalo para "esta oferta/pedido/conversación es de qué empresa" — crear ofertas, listarlas, pedir, contactar, dashboard). `primaryCompany()` = solo no-null si el usuario es el responsable principal (`is_primary=true`) — úsalo solo para "puede este usuario gestionar la empresa en sí" (editar perfil, añadir/quitar miembros; ver `CompanyPolicy::update`). Usar `primaryCompany()` donde tocaba `company()` deniega en silencio a cualquier miembro no-principal (mismo síntoma que el gotcha de `Gate::authorize` de arriba: no hay excepción, parece "no autorizado" legítimo). Ya pasó en 8 sitios a la vez (`OfferPolicy::create`, `OfferController::index/store`, `DashboardController`, `OrderPolicy::placeFor`, `PlaceOrderAction`, `ConversationPolicy::startFor`, `StartConversationAction`) precisamente porque nunca hay un test ni dato de prueba con un miembro no-principal — si añades algo nuevo que actúe "en nombre de la empresa del usuario", usa `company()` y añade un test con `is_primary => false`.
- **Solo un `superadmin` puede tocar roles desde Filament** (Fase 16, escalada de privilegios cerrada): el campo `roles` de `UserForm` está `disabled()` para cualquiera que no sea ya `superadmin` — si no, un `admin` podía autopromocionarse (o promocionar a cualquiera) a `superadmin`, el único distingo real entre esos dos roles en toda la app (`CompanyPolicy::delete`). Los campos `disabled()` de Filament no se guardan (no se "dehydratan"), así que esto no arriesga desasignar el rol a alguien que ya lo tenga cuando un `admin` guarda ese formulario por otro motivo. Si añades una acción nueva en Filament que pueda cambiar algo sensible a nivel de plataforma (no de una empresa/oferta concreta), pregúntate si de verdad cualquier `admin` debería poder hacerla o solo `superadmin`.
